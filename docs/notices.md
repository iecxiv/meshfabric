# Notices, Broadcast, Messages and continuity

## Sections and recipients

Notices is the received local inbox. Broadcast targets the effective server-authorized scope shown by its review dialog. Messages offers individual user notifications and notifications on devices with connected agents; this is not email, temporary device sharing or a chat history. User labels contain the name only; device labels contain device (group). Internal identifiers remain internal to routing.

Message search is hidden initially and toggled from the header. It matches visible labels, including group names. Closing it, changing section or switching Users/Devices closes and clears the filter. Sending remains subject to current connection, account permissions and device capabilities. Review the target and message; acceptance is not delivery or reading, and unknown results are not retried automatically.

## Persistent received notices

The inbox saves received entries, local read state and the corresponding unread count. It restores them after authenticating and binding the same server and account. The storage key uses a hash of the server URL and actor ID, not the session cookie. Other accounts/servers use separate files. Signing out hides and clears the current in-memory view, not its saved file. Restored entries are not posted again as Android alerts. Opening the inbox or dismissing an Android notification does not mark an entry read. Reading is local to this installation and is not a server read receipt.

All unread notices are retained; automatic retention keeps at most 200 read notices. Marking read does not necessarily delete the entry immediately. Individual deletion is explicit; clearing the inbox requires confirmation and also removes unread notices. Deletion affects only this local account/server inbox, not server events or messages. Previously discarded in-memory notices cannot be recovered retroactively.

## Storage and failure handling

NoticeInboxDisk uses AES-GCM with a key generated by Android Keystore, scope-bound authenticated data, atomic file replacement and app-private no-backup storage. This inbox does not fall back to plaintext. It is separate from remembered-login preferences and from unencrypted terminal archives. Clearing app data or uninstalling is not a supported way to retain this local inbox. Missing/unavailable keys or damaged ciphertext are reported rather than silently replaced with an empty inbox.

Reads and writes run on a serialized storage executor. Loading merges notices already received into memory; the UI reports loading, pending saves and errors. The plaintext payload limit is 16 MiB per server/account. Oversized/failed saves preserve the previous stored file rather than automatically deleting unread entries. New changes may exist only in memory. Wait until saving finishes before closing; abrupt process death can lose pending writes. Retry is explicit. Clearing after an error is destructive and requires the same clear-inbox confirmation.

Persistence preserves received data; it does not create push delivery, replay missed server messages or guarantee reception with a stopped process. Android notification permission and the account reception setting remain distinct.

## Background/resume boundaries

- Management preserves parent dialog navigation and cached presentation while blocking writes until current matching data is available. Identity changes clear context. Sensitive confirmations can invalidate; not every nested dialog is guaranteed to remain open.
- Server retains eligible open result dialogs independently of its paused reader and keeps their presentation state while still composed. Identity/observed-role changes retire them. Server-version updates keep their own authorization and confirmation flow; no update is replayed. Console/Trace output is still cleared on backgrounding.
- Events retains an open detail only for a verified lifecycle pause and same-binding reload. Fresh user authority must match. After reload there must be exactly one equal resolved record. Selection/inventory changes, main-connection loss, denial, errors or changed identity/authority close it.
- Activity is still a memory-only session journal, not the persistent Notices inbox. These continuity changes do not restore dialogs or live remote sessions after process death.

## Acceptance checks still required

Automated build, unit, lint and instrumentation runs are not proof of live-server delivery or physical-device lifecycle behavior. On the intended device: receive unread notices; wait for saving; close and reopen; verify unread/read state and count; switch accounts/servers and back; dismiss Android alerts without marking read; delete and clear then reopen; and background/resume each relevant dialog. Check real Broadcast/user/device delivery separately, including disconnection and insufficient permissions. No such manual scenario is declared complete here.
